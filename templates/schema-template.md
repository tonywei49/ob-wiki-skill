## 页面命名规范

- 主题页：`知识库/主题/{主题名}.md`
  - 例：`知识库/主题/AI编程工具.md`、`知识库/主题/大语言模型.md`
  - 只有研究方向明确后才创建
- 素材摘要：`知识库/素材摘要/{日期}-{短标题}.md`
  - 例：`知识库/素材摘要/2026-04-05-karpathy-llm-wiki.md`
  - 每篇素材只生成一篇；详细提炼优先写在这里
- 对比分析：`知识库/对比分析/{对比主题}.md`
  - 例：`知识库/对比分析/工具选型.md`
- 综合分析：`知识库/综合分析/{分析主题}.md`
  - 例：`知识库/综合分析/AI工具选型建议.md`

## 交叉引用规范

- 页面间使用 Obsidian 双链连接真实页面；不要在说明文字里写假的双链占位符
- 素材引用格式：`[来源: 素材标题](../素材摘要/xxx.md)`
- 每个页面底部维护"相关页面"列表
- `sources:` 是给 llm-wiki 和图谱权重使用的来源信号，不等同于 Obsidian 图谱连线
- 原始素材可以单向链接到对应素材摘要；素材摘要不要用 Obsidian 双链反向链接原始素材，只在 `source_path` 或普通文本里记录路径
- 如果原始素材和素材摘要同名，原始素材文件名追加 `-raw`，避免 Obsidian 双链歧义

## 页面格式规范

每个 wiki 页面应包含：

```markdown
---
tags: [标签1, 标签2]
created: YYYY-MM-DD
updated: YYYY-MM-DD

## 正文内容

- 又一个真实页面
```

## Ingest（消化素材）规则

### 项目归属

新增内容写入前，必须先判断它是否属于当前 wiki 的长期研究项目，并把判断结果、目标 wiki、建议主题和将写入的页面类型交给用户确认。用户确认前，不要复制原始素材，也不要写入素材摘要、主题、对比分析、综合分析或研究方向。

如果同一个 wiki 内有 2 个以上相近主题都能归类，必须先列出候选主题、差异和推荐项，让用户确认放到哪个主题，或是否新建主题。

### 分级处理

根据素材长度和信息密度自动分级：

**完整处理**（素材 > 1000 字）：
1. 每个新素材**必须且只生成一篇**摘要页（`知识库/素材摘要/` 下），详细提炼写在这里
2. 提取素材中对用户有价值的信息，写进该素材摘要页
3. 只有 `研究方向.md` 已由用户确认填写，并且素材匹配这些方向时，才检查是否需要创建或更新主题页（`知识库/主题/`）
4. 更新 `索引.md`（添加新条目）
5. 更新 `日志.md`（记录操作）
6. 更新 `总览.md`（如果知识库全貌有变化）

**简化处理**（素材 < 1000 字，如短推文、小红书笔记）：
1. 生成摘要页（`知识库/素材摘要/` 下）
2. 提取 1-3 个关键概念
3. 更新 `索引.md` 和 `日志.md`
4. 跳过主题页和 总览.md 更新

### 来源边界

这套边界和安装输出、状态说明、回归测试保持一致。

| 分类 | 当前来源 | 处理原则 |
|------|----------|----------|
| 核心主线 | `PDF / 本地 PDF`、`Markdown/文本/HTML`、`纯文本粘贴` | 不依赖外挂，直接进入主线 |
| 可选外挂 | `网页文章`、`X/Twitter`、`微信公众号`、`YouTube`、`知乎` | 先自动提取；失败时退回手动入口 |
| 手动入口 | `小红书` | 只接受用户手动粘贴 |

### 素材类型路由

| 来源 | raw 目录 | 提取方式 |
|------|----------|----------|
| 网页文章 | `原始素材/网页文章/` | baoyu-url-to-markdown skill |
| X/Twitter | `原始素材/推文/` | baoyu-url-to-markdown skill（需 Chrome 登录） |
| 微信公众号 | `原始素材/微信公众号/` | wechat-article-to-markdown |
| YouTube | `原始素材/网页文章/` | youtube-transcript skill |
| 小红书 | `原始素材/小红书/` | 用户手动粘贴内容 |
| 知乎 | `原始素材/知乎/` | 用户手动粘贴内容 或 baoyu-url-to-markdown skill |
| PDF / 本地 PDF | `原始素材/PDF/` | 直接读取 |
| Markdown/文本/HTML | `原始素材/笔记/` | 直接读取 |
| 纯文本粘贴 | `原始素材/笔记/` | 直接使用 |

## 别名词表（Alias Table）

用于 query 和 digest 时自动展开搜索。搜索任意一个词，会同时搜索同一行的所有别名。
AI 在 ingest 时如果发现新的同义词关系，可以建议用户添加。

格式：每行一组同义词，用 `=` 分隔。

```
LLM = 大语言模型 = 大模型 = Large Language Model
RAG = 检索增强生成 = Retrieval Augmented Generation
fine-tuning = 微调 = 精调
prompt engineering = 提示工程 = 提示词工程
```

维护原则：
- 只收录在你的知识库里**实际出现过**的同义词，不要预填一堆用不到的
- 每组控制在 5 个以内，太多说明概念本身需要拆分
- 中英文混用时把最常用的放第一个
- ingest 发现新的同义词关系时，AI 应主动建议添加到此表

## Query（查询）规则

1. 先读 `索引.md`，定位相关条目
2. 用 Grep 在 `知识库/` 下搜索关键词
3. 阅读相关页面后综合回答
4. 回答中标注来源页面（引用链接）
5. 查询结果不保存到 `知识库/查询/`；如果用户明确要求写入，再走 digest 或 crystallize

## Lint（健康检查）规则

1. 检查范围：随机抽查 10 个页面 + 最近更新的 10 个页面
2. 检查项：
   - 页面间矛盾（不同页面说法不一致）
   - 孤立页面（没有其他页面链接到它）
   - 缺失概念页（被某概念链接但实际不存在）
   - 缺少交叉引用（相关页面之间没有互相链接）
   - index 一致性（索引.md 记录与实际文件是否对应）
   - Obsidian 图谱孤点（根目录页、原始素材、schema 是否在 Obsidian 图谱里孤立）
3. 输出中文报告，对每个问题给出修复建议
4. 如果发现问题，询问用户是否自动修复

## 关系类型词汇表（可选，用于手动标注知识图谱）

这张表提供 graph 工作流生成的 `知识库/knowledge-graph.md` 里**可选**的关系类型词汇。
AI 生成图谱时默认全部用 `-->`（无标注），不自动判断关系类型。如果你想让图谱
更清楚地表达节点之间的语义，可以用编辑器把最重要的几条箭头改写成带标注的形式：

| 类型关键词 | 含义 | Mermaid 写法示例 |
|-----------|------|-----------------|
| 实现       | A 是 B 的具体实现 | `A -->|实现| B` |
| 依赖       | A 依赖 B 才能工作 | `A -->|依赖| B` |
| 对比       | A 与 B 是同类可以比较 | `A -->|对比| B` |
| 矛盾       | A 与 B 存在观点冲突 | `A -->|矛盾| B` |
| 衍生       | A 从 B 演化而来 | `A -->|衍生| B` |

使用原则：
- 只标最重要的 3-5 条关系，不要强行给所有箭头打标
- 不确定的关系保持默认 `-->` 箭头
- 自定义类型控制在 2 个以内，避免词汇表膨胀
- 标注后在 Obsidian / VS Code（Markdown Preview Enhanced）/ Typora 里重新渲染就能看到标签
